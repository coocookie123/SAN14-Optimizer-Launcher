# AI 行为树工具

给「[W]三国志14优化启动器」以后的 AI 优化功能打基础：读懂、改写游戏的 AI 行为树，并在看海时记录 AI 的表现。和跳过报告一样，不往游戏目录放文件，游戏文件只读不写。

## 现状（2026-11-11）

- 行为树文件能完整解析，写回后和原文件逐字节一致（`bt.bin`、`bt_ex.bin`、`bt_exce.bin` 都验证过）。
- 节点类型全部对上类名：游戏节点 285 种，引擎内置节点 13 种。
- 能把四棵树导出成可读的缩进文本，条件节点显示成表达式。
- 观察工具：游戏数据的主要字段已在看海中实机核对；`observe.py` 按月记录各势力状况和城市易主等事件。
- 改树注入已跑通（2026-11-11）：`btpatch.py` 按补丁清单生成改版树，`launch.py` 挂起启动游戏并早期注入 `bin/san14_ai.dll`，游戏读到的是改版。已接进「[W]三国志14优化启动器」的「电脑 AI」区（八个模块：出兵编成、集结齐进、会战协同、野战撤退（2026-11-13 起是第四版之四）、城下迎击、攻城评估（2026-11-13 加，11-14 起是第二版：出兵门槛算上守方府加成和按实测权重的邻城援军，DLL 功能 siegefu；当晚又加城外集结、先占府，DLL 功能 fu、siegeprep；11-15 再加防断粮，DLL 功能 supplyguard），城下迎击 11-15 晚并入援军继续守（DLL 功能 relief），以及走 DLL 每日执行层的雁行站位和守关（2026-11-14 加，第 5.1 版）；会战协同的每日攻击目标分配也走 DLL；2026-11-16 用户定把七个做好但没开的 DLL 功能并进这八个模块：城下迎击加 defend（守城迎击）、ford（渡江迎击，带树补丁）、shore（半渡而击）、navaldef（水战守港第 1.1 版），会战协同加 waitfight（贴敌待命改还手），集结齐进加 siegelone（攻城落单不单打），攻城评估加 siegeenough（攻城凑够才出）；同时删掉 siegecomp、siegesplit、siegefight、cut、portguard 五个功能的代码和模块文件，见 `BEHAVIOR_PLAN.md` 第五十节），实机测试一律从启动器启动（自动测试 `autotest.py` 用同样的命令行）。

## 用法

```bash
python -P ai/btdump.py                 # 导出到 ai/out/：tree0_force.txt 等四个文件和 summary.txt
python -P ai/btfile.py <bt_exce.bin>   # 只解析并检查能否原样写回
python -P ai/make_node_types.py        # 游戏更新后重建 node_types.json（要先用 tools/dump.py 导出新的内存映像）
python -P ai/gamedata.py survey        # 游戏开着时：列出数据根下的各个对象数组和类名
python -P ai/gamedata.py dump city 3   # 看某个对象的原始字段
python -P ai/observe.py                # 看海记录：游戏关掉或 Ctrl+C 停止，结果在 ai/runs/<开始时间>/
python -P ai/observe.py summary        # 汇总最近一次记录（不含异民族）
```

## 改树注入（`btpatch.py`、`launch.py`、`bin/san14_ai.dll`）

```bash
python -P ai/btpatch.py ai/modules/a.json b.json  # 只生成改版树到 ai/build/，可加 --check 只检查、--show 列出改动
python -P ai/launch.py ai/modules/a.json ...      # 生成改版树并用它启动游戏（Steam 要开着，游戏要关着）
python -P ai/btsrc.py --selftest                  # 树的文本写法往返测试
python -P ai/test_btpatch.py                       # 改树工具的测试
python -P aihook/build.py                         # 重编 DLL
```

- 行为模块（`ai/modules/*.json`）用导出文件同样的写法写新逻辑，支持改参数、插入、包裹、替换、删除，按节点文本定位并核对命中个数。几个模块一起用时会检查冲突。格式见 `btpatch.py` 开头的说明，设计见 `BEHAVIOR_PLAN.md`。原值或位置对不上（比如游戏更新改了树）就整份拒绝，不会拿旧补丁覆盖官方的 AI 修正。改完会重算树的校验值，并确认能原样解析回来。
- `launch.py` 跳过官方启动器，直接以挂起状态启动 `SAN14CE_SC.exe`（工作目录是游戏目录，设好 `SteamAppId`），把 `LoadLibraryW(bin/san14_ai.dll)` 作为 APC 排到主线程上再恢复。DLL 在游戏代码运行前加载，替换游戏自己和 kernel32 导入表里的 `CreateFileW`：游戏打开 `0000/bt_exce.bin` 时改开环境变量 `SAN14_AI_BT` 指定的文件，其他文件不动。日志在 `analysis/ai_dll.log`（会记前 40 次打开文件和每次重定向）。
- **DLL 每日执行层**（2026-11-12）：模块可以写 `"dll": ["stance"]`，`launch.start(features=…)` 经环境变量 `SAN14_AI_FEATURES` 传给 DLL（A/B 用 `SAN14_AI_AB`）。A/B 默认所有模块一起分组；`autotest.py --ab odd:defend`（冒号后是模块 id，多个用 `+` 连）只让这几个模块按奇偶分组，其余模块所有势力都开，用来单独测一个模块（2026-11-12）。有功能开着时，DLL 在游戏读树那一刻按 `sigs/sigs.json` 里特征 `ai_dll` 的几条特征码找到数据根、`CProgressState` 虚表和部队设定函数，换掉推进状态的 Update，每换一天在游戏线程里跑一遍功能。设计和核对方式见 `BEHAVIOR_PLAN.md` 第二十四节；`python -P aihook/build.py --test` 离线核对定位结果。自动测试加 `--dev` 时直接用本仓库的脚本、模块和 DLL，不用先重建发布包。
- **树探针**（2026-11-12，调试用）：模块写 `"dll": ["probe"]` 时，DLL 换掉原版日志节点 `CMiscLogNode` 的执行函数（原版的打印已编译掉，只读参数、返回成功；第一个参数大于 18 时什么都不做）。树里写 `MiscLogNode(99, 0, $m.<模块>.<名字>)` 的地方每执行一次计一次数，DLL 每天把计数写进 `logs/ai_dll.log`（`probes: 键=次数`）。`python -P ai/research/probe_log.py logs/ai_dll.log ai/modules/<模块>.json` 按变量名汇总，用来查改树后每个分支一年走了几次、卡在哪个条件。探针不改行为；特征码是 `sigs/sigs.json` 的 `misclog_vtable`、`misclog_execute`（可选，找不到就不挂）。
- **府加成实测**（2026-11-12，调试用）：`modules/experiments/bonuslog.json` 打开 DLL 功能 `bonus`，每天调用游戏自己的府加成函数（特征码 `area_bonus_fn`，2b2b30）算每支部队的实际加成，连同所在区域的府主人、涂色格数、区域里的敌军、有没有敌军踩在府上，变了就记一行；`python -P ai/research/bonus_log.py logs/ai_dll.log` 汇总。看海记录从同一天起也带区域、府主人和府分（`observe.py` 开头的说明），`research/fu_stats.py` 按府分差看交换比、看原版踩府。结论见 `BEHAVIOR_PLAN.md` 第三十二节。
- 引擎规则（2026-11-12 读代码核实）：`LoopListElementNode` 每个元素按顺序跑子节点，遇到失败就结束这一轮、接着下一个元素；`MiscBreakNode` 设一个中断标志，子节点之间和每轮之后都查，循环随即停下。所以循环体里直接写一串 IF 就是逐条筛选。`SEQ(0, 2, 1)` 子节点失败也返回成功，适合包可选的步骤。
- **水战、半渡而击**（2026-11-13，试验）：地形表 `research/terrain_exce.bin`（每格 1 字节，格子对象 +0x10，从内存导出：14 江面、24 另一种水面、18 港、16 城、15 府、17 关、19 山、23 海和地图外）和区域表 `research/area_exce.bin`（每格 u16）。`research/naval_stats.py` 统计水面部队日、水上和陆上接战的掉兵、渡江时守方在不在。`modules/experiments/shore.json` 打开 DLL 功能 `shore`：敌军在水面时派岸上的近战部队贴着它打（详见模块说明和 `BEHAVIOR_PLAN.md` 第三十八节）；`research/shore_check.py logs/ai_dll.log ai/runs/<局>` 看贴上几次、双方掉兵。每局测完要把 `logs/ai_dll.log` 复制进该局目录（下次开游戏会覆盖）。
- 游戏只在启动时读一次树，所以改版只对这样启动的游戏有效；从 Steam 正常启动就是原版。画面等设置照样从注册表读（官方启动器上次设的）。直接运行 `launch.py` 时不带跳过报告和府加成；从启动器勾选时，启动器传 `--ai id,id` 给 `tools/report_button.py`，由它调用 `launch.py`（`steam_game_dir()` 找游戏目录、`btpatch.build(source=…)` 编树、`start()` 早期注入），其余功能照常。编树或注入失败时退回普通启动（原版 AI），并在游戏里提示；DLL 日志写到 `logs/ai_dll.log`，结果记在 `logs/helper.log`（`ai modules active` / `NOT active`）。发布包里的 `app/ai/` 只带运行需要的脚本和这五个正式模块（试验模块在 `modules/experiments/`，退役的在 `modules/archive/`）。
- 2026-11-11 实测：游戏启动 3.7 秒后读树，重定向成功，游戏正常。测试模块 `modules/experiments/test_day2.json` 把势力树「每月 1 日重选攻打目标」改成 2 日，看海 13 个月（194-07 到 195-07）攻打目标一次没变，6 个势力从开局到最后都没有目标；原版 11 个月里换了 47 次，全在 1 日。说明游戏按改版的树决策，而且势力树只在每月 1 日运行。这个补丁只用来测试，会让电脑不再重选目标，不要日常用。

## 看海记录（`observe.py`）

游戏开着、进到大地图后运行。每秒读一次内存（一轮约 0.02 秒），只读不写：

- `forces.csv`：每月一行一个势力，记城市、军团、现役武将、城内兵力、出征部队数和兵力、资金、兵粮、攻略目标，异民族单独标出。
- `cities.csv`：每月一行一座城，记所属势力、兵力、资金、兵粮、士气、太守。
- `events.csv`：随时记城市易主、势力灭亡、势力出现、君主更替、攻略目标变更；读档或新开局（日期倒退或一下跳过 40 天以上）也会记下来。日期动起来之前什么都不记，所以标题画面的演示数据和开局加载中的数据不会混进来；汇总只看最后一次开局之后的部分。
- `meta.json`：开始时间、游戏版本、起始日期。

结束时会打印汇总：各势力城市数和兵力的起止变化、存活月数、各类事件次数、最近的城市易主。以后改了 AI，用同一个剧本跑两次，比较汇总就能看出效果。出征部队按「主将所在地 == 61 + 部队序号」判断还在场上；武将身份 1、3、4 算现役。还没记录 AI 每个决策节点的执行次数，那需要在节点执行函数上挂钩。

首次实测（2026-11-11，194 年剧本看海，195-03 到 196-01，约 10 分钟）：城市易主 5 次、势力灭亡 1 个、独立 1 个，汇总和事件逐条对得上。攻略目标变更 47 次全在每月 1 日，说明势力树的目标选择每月跑一次（树里「日 == 1」的条件）。

`ai/out/`、`ai/runs/` 是从游戏数据生成的，不进仓库。

## 文件格式（`0000/bt_exce.bin`）

全部是小端 u32。

- 文件头：`JBTP`、版本 2、树的数量 4、0，然后每棵树一条（偏移、大小、哈希）。哈希是这一段的 CRC32 按字节反序存放，改树后要重算（`btfile.section_hash`）。
- 每棵树：`TB1G0000` 头（0x20 字节）、`IZSG0000` 块（0x18 字节），然后是 `ITBG0000`（树本体）和 `IBBG0000`（黑板定义，四棵树都是空的）。块头 16 字节：标记 8 字节、含块头的大小、0。
- 树本体：`KTBT`、版本 1、树名哈希、0、节点数，然后是节点：
  - flags、类型哈希
  - flags & 4 时：一个额外值
  - 父节点序号（根节点为 -1）、子节点数
  - 参数个数 n、n 个参数
  - flags & 2 时：长度和名字（Shift-JIS，目前只有调试日志节点有）
  - flags & 8 时：第二个参数表（只有 OneSelector 用）
- 节点按前序排列，父节点总在子节点前面。flags & 1 表示游戏节点，否则是引擎内置节点。
- 游戏在程序启动时读一次这个文件（RVA `153080` → `c0ca0`），读档时不重读。

## 节点

- 游戏节点由工厂函数按类型哈希创建（1.0.2.58226 的 RVA `1ad90`）。参数交给节点自己的读参数函数（虚表第 17 项），每种节点含义不同。虚表第 13 项返回类名，第 16 项是执行函数。
- 内置节点在树加载函数里按哈希创建（RVA `b2d084` 附近），类名由虚表第 12 项返回：Root、Sequential、Selector、OneSelector、Priority、Parallel、Probability、ConditionDecorator、LoopDecorator、ReverseDecorator、Joint、StaticLink、DynamicLink。
- 参数里大于 0xFFFF 的值基本是黑板变量的哈希（变量名没有存在文件里），小数字是常量或枚举。

## 条件节点（ConditionDecorator）

参数：`[整体取反, 全部满足(1)/任一满足(0), c, 项数, 各项…]`。每一项：`kind, 取反, 函数编号, x, 操作数个数, 操作数…`。

- kind 2：调用条件函数。kind 0：后面 x 项全部满足才算真。kind 1：[推测] 后面 x 项任一满足（只看了代码结构）。
- 条件函数由游戏的一个回调统一分派（RVA `c3160`，按编号减 1 查跳转表，共 167 个）。`make_node_types.py` 能自动认出简单比较：18 是变量 > 变量，19 是变量 ≥ 变量，20 是变量 > 常数，21 是变量 ≥ 常数。另外几个等于、不等于是按代码形状猜的。
- 手工读过的条件函数写在 `btdump.py` 的 `CONDITION_NAMES` 里，导出时显示成 `C65:玩家军团(...)`：22 有效、23 相等、26 军团方针（军团 +0x15，含义待实机核对）、28 部队任务、29 部队行动、63 玩家势力、65 玩家军团、115 难度（0 初级到 4 顶级）、116 玩家坐大（没读完）。名字带 `?` 的是推测。其余函数导出里写成 `C编号(...)`。
- 顺序节点 `SEQ(0, 模式, 1)` 的模式按树的写法判断（没看引擎代码）：0 是依次尝试、第一个成功就停（相当于 if/else if），1 是依次执行、有一个失败就停，2 是全部执行。

## 属性编号（`info_names.json`）

读属性的节点写成 `VariableGetPersonInfoNode(对象, 编号, 输出变量)`，`GetMyself*InfoNode(编号, 输出变量)`。编号的含义整理在 `info_names.json`，导出时显示成 `21:可带兵数`。树里约 1900 次读属性，现在约 86% 有名字，其中约 4 成是推测（带 `?`）。

- 查法：每个读属性节点的执行函数（虚表第 16 项）按编号查跳转表，每个编号读一个字段或调一个取值函数。再看 exe 里有 RTTI 名字的事件脚本类（`SCompareCityMoney@S14Event` 这类，共 453 个）是不是读同一个字段、调同一个函数，最后对照树里的用法。能力顺序（统率、武力、智力、政治、魅力）和难度名取自界面文本。
- 武将 +0x1a2 到 +0x1b8 有 12 个带符号的隐藏参数，取值只有 -20、-10、0、10、20，树里大多用在君主身上。31（+0x1b2）是对汉室的态度：事件类 `SComparePersonKanshitsu`（漢室）读它，实机刘备、马腾、孔融 20，袁术、张鲁、公孙度 -20。13 像好战（孙策、吕布、李傕 20，刘璋、孔融 -20），14 像重义（刘备、马腾 20，吕布、袁术 -20），32 像野心（刘表 -10，刘璋 -20）。其余的名字查不到，导出里写成 `隐藏参数1a6?`。
- 2026-11-11 看海实机核对（194 年剧本，只读内存；邺城、濮阳的资金、兵粮、士兵、士气、太守、负责募兵和负责训练都和游戏界面逐项对过）：城市 +0x34 资金、+0x38 兵粮、+0x3c 兵力、+0x44 士气；武将 +0x11e 身份（君主 1、现役 4、在野 7）、+0x120 忠诚、+0x124 起五个字节是基础能力；势力 +0x10 君主、+0x13 起是友好度表、+0x17a 是攻略目标势力；军团 +0x10 势力、+0x12 都督。城市 +0x94、+0x98 不是界面上的收入或支出，是大负数，像 AI 自己算的资金和兵粮余裕。
- 军团树按军团 +0x15 分三支（条件 26）。看海时 20 个电脑军团这个值全是 0，所以电脑军团只走第 0 支，第 1、2 支约 6000 个节点暂时用不上。这个值什么时候不是 0 还不知道。
- 有几个编号（势力 8、武将 25、据点 33）的代码写入的是黑板里一个指针的低 32 位，跟游戏数据无关，像是没实现。势力树却拿势力 8 和 15 比，这个判断的结果取决于内存地址。
- `research/` 里是查编号用的脚本，路径写死在脚本里，在输出目录下运行：`evindex.py` 建「函数 → 事件类」和「字段 → 事件类」索引，`info_cases.py` 列出每个编号读什么、树里怎么用，`msg.py` 解 `msgdata*.bin` 并按正则搜界面文本。

## 每局测试后的检查（`research/check_modules.py`）

