## 使用说明

**功能**

- 每回合开头不再弹出要点两次确认的「行动报告」「收支报告」，直接进入战略阶段。
- 地图左下角「执行建言」按钮右边多一个「回看报告」按钮，点一下就弹出本回合的原版报告，照常点两次确认关掉。

**需要**

- 三国志14 威力加强传承版套装，Steam 版，简体或繁体中文。
- Python 3.13（Microsoft Store 版即可）和 Pillow（`python -m pip install --user pillow`）。

**启动**

- 双击桌面上的「三国志14 跳过报告」。它会通过 Steam 打开游戏，在游戏自带的启动器里照常点开始就行。
- 也可以不用桌面快捷方式，在 Steam「属性 → 启动选项」里填下面这一行，然后照常从 Steam 启动：
  ```
  "<pythonw.exe 的完整路径>" -P "<本工程目录>\tools\report_button.py" %command%
  ```
- 桌面快捷方式丢了可以重建：`python -P tools/make_shortcut.py`。

**注意**

- 按钮由 `bin/san14_overlay.dll` 直接画进游戏画面，全屏、无边框、窗口模式都能用（2026-11-11 全屏实测可以点击）。DLL 注入失败时，会退回成悬浮在游戏上面的小窗口，这种方式只在窗口模式和无边框模式下看得到。
- 无边框模式下，屏幕每隔半分钟到一分钟会闪一下，这是游戏或显示设置本身的现象，不装 mod 也一样（2026-11-11 对比确认），全屏模式下不会。如果介意，可以试试把 NVIDIA 控制面板里的 G-SYNC 改成「仅全屏模式」。
- 不往游戏目录放任何文件，只在游戏运行时改内存。游戏关闭后一切恢复原样，Steam 校验文件也不受影响。
- 游戏更新后，如果补丁位置对不上，工具就不跳过报告，游戏照常弹出报告，地图左下角会显示约 12 秒「游戏版本 x.x.x 未适配，已停用」，这时需要重新适配（见下面「游戏更新后怎么适配」）。判定条件：游戏窗口出现 15 秒后（代码早已解密）仍找不到特征码，或者要改的字节和预期不一样。这时会按 `sigs/sigs.json` 逐个功能再查一遍：府加成、看海接管对得上就照常运行，提示改为「部分未适配，已停用……，其余照常」。游戏 exe 的版本号每次都会写进日志，已测试版本是 `report_button.TESTED_VERSIONS` 加上清单里标了 `tested` 的版本。想看提示的效果，可以在游戏开着、按钮程序没运行时执行 `python -P tools/report_button.py --notice-test`。
- 启动器的游戏目录默认留空，通过 Steam 启动。没有 Steam 时，可以选择游戏目录，启动器会直接运行该目录里的 `SAN14_Launcher.exe`（工作目录设为游戏目录）；补丁对其他来源的 exe 是否生效，取决于它的代码和 Steam 版是否一致。
- 运行日志：`analysis/helper.log`（按钮程序）和 `analysis/overlay_dll.log`（游戏里的 DLL）。每次启动时，上一次的日志会改名为 `*.prev.log`，所以只保留最近两次。单次运行最多写 1 MB 和 256 KB，同一条错误一分钟内只记一次。

**和「三国志14 优化伴侣」一起用**

- 照常用本工具（或「[W]三国志14优化启动器」）开游戏，读档后再开伴侣、勾上它的「略过旬末报告」。
- 伴侣挂上之后，跳过报告交给伴侣，本工具自动让开；「回看报告」按钮改为替你按一下 F8，用伴侣自己的「打开本旬报告」。伴侣没开「略过旬末报告」时，F8 不起作用，本工具会自己弹出报告。伴侣关掉后，本工具自动恢复跳过。
- 判断方法：伴侣用 Frida 改写 `CUserStrategyState::Update` 里读子阶段的那条指令（`+0x16`，原为 `8B 86 70 04 00 00`）。DLL 每次调用都比对这 6 个字节，不一样就不跳过，并在共享内存里置 `foreign_hook = 1`。
- 先开伴侣、后开本工具也可以，但伴侣改过的代码会让 DLL 的特征码对不上，这时只能用第 5 版补丁；伴侣关掉后，回合开头会恢复约 2 秒的停顿，直到重开游戏。

**自定义府加成**

- 启动器里勾「自定义府加成」，分别填我方和电脑的值（0～100），「预设」三个按钮是原版高级 4/4、超级 4/16、顶级 4/24。只在启动游戏时写一次，改了要重开游戏。
- 原理（`tools/area_bonus.py`）：府加成计算函数（`2b2b30`）先读「我方」值；电脑势力在超级难度改读「超级」值，顶级难度改读「顶级」值。这三个值是 exe 里写死的 `.data`（磁盘上就是 4、16、24），只有这个函数读、没有代码写，所以运行时写一次就一直有效。我们写「我方」和两个电脑值，不改代码。
- 和优化伴侣的差别：伴侣还把这次调用的难度强制当成顶级，所以它的电脑值在所有难度都生效；但它会对这个函数和难度函数做代码哈希校验，我们一改代码它就整体拒绝启动。所以我们只改数据：初级到高级时电脑和我方用同一个值（原版规则）。
- 不跳过报告、只改府加成时，启动器传 `--no-skip --area-bonus P,C`，按钮程序写完就退出。调试：`python -P tools/area_bonus.py status | set 4 24 | restore`。

**陷阱近身触发**（2026-11-14 加，默认不勾）

- 启动器「陷阱」一节勾「陷阱近身触发」（`settings.ini` 的 `trap_near`），传 `--trap-near`。陷阱、猛火陷阱、落石原来敌军进入 2 格内就发动，改成走到陷阱那一格或紧挨的 6 格才发动；伤害、状态异常和效果范围照原版。火陷阱、火船本来就是 1 格。双方的陷阱一样处理（用户定）。用户说的「火焰球类」：游戏里没有叫这个的设施，设施种类一共 17 种（数据根 +0x73958，名字在 +0x10），火攻的是火陷阱、猛火陷阱、火船，它们和陷阱、落石同属类别 4，走同一个每日判定和同一个发动范围取值函数，所以同一个钩子一起处理。军乐台、箭楼、投石台、阵、砦、石兵八阵是常驻设施，另一步（`18f620`）每天直接对范围内的部队起作用，没有「触发」，不改。
- 原版逻辑（1.0.2.58226 读代码）：`CProgressState::Update` 每天推进时跑一步 `18f7e0`，逐个地图设施（`CObjectData`：+0x10 格、+0x12 设施种类、+0x13 势力）取「发动范围」`191080(种类)`，用 `2b0500` 收集设施格这么多格以内的部队，有敌方部队就调用效果函数 `191d60`、再移除设施。效果函数按「效果范围」（另一个取值函数 `bae80`：+0x37，加政策的「陷阱影响范围」）取格子，按两个效果槽分别收集部队施加伤害和状态异常。设施种类数据（`CFacilityData`，数据根 +0x73958，每项 0x68 字节）里的数值另存一份编码副本（+0x50 起 19 项，循环移位再异或种类序号），游戏读的是副本，所以直接改原始字段没用。发动范围（+0x40）：陷阱 / 猛火陷阱 / 落石 2，火陷阱 / 火船 1，其他设施 0；类别 +0x2c：4 是陷阱。`191080` 只有触发判定和设施说明里显示「发动范围」的两个函数调用，AI 不读。
- 改法：`bin/san14_ai.dll` 在游戏读行为树时（代码已解密）按特征码 `trap_trigger` → `trap_act_range` 找到 `191080` 挂内联钩子：类别 4 的种类大于 1 时返回 1。类别偏移和陷阱的类别值从 `191d60` 里游戏自己的判断（`trap_category`）读。所以这个功能和改树一样要由我们启动游戏：按钮程序勾了它就用 `ai/launch.py` 启动（没勾 AI 模块就不换树），环境变量 `SAN14_TRAP_NEAR=1`；没生效（特征码对不上等）时游戏里提示约 12 秒，本局陷阱照原版。DLL 日志 `logs/ai_dll.log` 有 `trapnear installed` / `NOT installed`。
- 测试：`--trap-log`（环境变量 `SAN14_TRAP_LOG=1`）再挂 `191d60`，每个陷阱发动时记一行，带游戏判定那一刻他国部队离它几格；`python -P ai/research/trap_check.py logs/ai_dll.log` 按种类汇总。自动测试：`python -P ai/autotest.py --ai none --trap-log [--trap-near] --dev --slot 4 --start 206-1-1 ...`。
- 实测（2026-11-14，存档 4 号 206-1-1 看海两年，原版 AI，地图上火陷阱 52、陷阱 22、落石 10、猛火陷阱 0）：原版（`ai/runs/20261114-203843`）陷阱发动 4 次，发动时最近的他国部队 3 次在 2 格、1 次在 1 格；开近身触发（`ai/runs/20261114-202136`）陷阱发动 8 次，全在 1 格。火陷阱两边各 4 次，都在 1 格（本来就是 1，说明日志的位置和游戏判定一致）。同一个陷阱（25 号势力，格 31208）原版在 206-4-18 敌军 2 格时发动，改后 206-4-20 敌军到 1 格才发动。落石建在山地类地形（地形码 8、9），两局都没发动过。两局都正常跑完两年；游戏目录没有文件变动。

**电脑 AI（试验）**

## 用法

用 `python -P` 运行（Frida 装在用户级 site-packages，用 `-I` 会导入失败）。

日常使用，在 Steam「属性 → 启动选项」里填下面这一行，点「开始游戏」后会自动打补丁、显示按钮，游戏关闭后自动退出：

```
"<pythonw.exe 的完整路径>" -P "<本工程目录>\tools\report_button.py" %command%
```

也可以在游戏开着时单独运行 `pythonw -P tools/report_button.py`。日志写在 `logs/`。0.3.0 起去掉了快捷键（用户觉得暂时用不上）。

调试用：

```bash
python -P tools/patch.py waitnew 1800   # 等新启动的游戏解密完成后自动打补丁
python -P tools/patch.py status         # 查看补丁状态
python -P tools/patch.py restore        # 恢复原始代码
```

## 游戏更新后怎么适配

Mod 用到的全部特征码、从命中处取的偏移、代码依赖的原始值和 RTTI 类名，都集中在 `sigs/sigs.json`（下称清单）。Python 脚本运行时直接读它；DLL 的特征码由 `overlay/build.py` 从清单生成 `overlay/sigs_gen.h`，结构偏移也改成从匹配到的游戏代码里读。清单格式见文件开头的 `_说明`。

**游戏更新后会发生什么**：启动器照常能开游戏。跳过报告对不上时，不再整体停用：按清单逐个功能检查，府加成和看海接管对得上就照常运行，游戏里提示「游戏版本 x 部分未适配，已停用跳过报告……，其余照常」；都对不上才提示「未适配，已停用」。

**适配步骤**（以从 1.0.2.58226 更新到新版本为例）：

1. **开游戏**：用「[W]三国志14优化启动器」或 Steam 启动，等到标题画面（这时 SteamStub 已经把代码解密）。
2. **导出镜像**：`python -P tools/dump.py`，得到 `analysis/dump_<exe 修改时间>_<版本号>/`（`image.bin` 约 44 MB，加 `meta.json`）。
3. **检查**：`python -P tools/sigcheck.py`。游戏开着时检查运行中的游戏，并读几个武将名、城市名、势力君主和日期，确认数据结构没变（要先进剧本，标题画面会跳过这一项）；游戏没开时检查最新的镜像，也可以 `--version <版本号>` 或 `--dump <目录>`。按功能输出「可用 / 不可用」和原因，`-v` 列出每条特征码。全部可用就直接到第 6 步。
4. **找回特征码**：`python -P tools/sigfind.py --old 1.0.2.58226 --new <新版本号>`（也可以写镜像目录，`--new live` 是运行中的游戏）。对每条失效的特征码，它先用 `where` 和锚点（RTTI 虚表槽位、引用的字符串、调用关系、常数、引用的全局变量）在新镜像里找候选函数，再和旧函数逐条指令比较（忽略地址），对齐后把旧特征码和每个字段映射过去，生成新特征码（相对跳转和 rip 偏移改成 `??`，旧特征码里补丁位等通配照搬），验证全镜像唯一，最后按清单的 expect 等规则再查一遍。结果存到 `analysis/sigfind_<新版本号>.json`：
   - **已找回**：新特征码通过了全部检查。
   - **需要人工确认**：一般是代码依赖的值变了（比如结构偏移 0x470 变成 0x478），或者相似度偏低。看提示里的 `expected ...`：DLL 和带 `soft` 的字段是运行时从代码里读的，不用改代码；其余要先改对应的代码（`patch.py`、`ai/gamedata.py`、`takeover.py` 等，`tools/test_sigs.py` 列出了这些常数），再改清单里的 `expect`。
   - **没找到**：用 `tools/disx.py`、`ai/rtti.py` 手工找，在清单里给这条加一个变体。
5. **确认后写回**：`python -P tools/sigfind.py --old 1.0.2.58226 --new <新版本号> --write`，逐条问要不要写（`--yes` 只写「已找回」的）。新特征码作为新变体追加，旧版本的变体保留；随后自动把新版本加进清单的 `versions`，记录各条的 RVA（和 `sigcheck.py --record` 一样）。
6. **验证**：
   - `python -P tools/sigcheck.py --version <新版本号> -v`：全部可用。旧版本的镜像也应该照样全部可用。
   - `python -P tools/test_sigs.py`：清单格式、各版本镜像上的 RVA、Python 各模块的定位代码（用假进程在镜像上跑）、代码里残留的常数、DLL 头文件是否最新。
   - `python -P overlay/build.py --test`：重编 DLL，在镜像上跑 DLL 的定位代码，逐个地址和 `tools/sigs.py` 的结果比对。
   - AI 改树：`python -P ai/make_node_types.py` 重建 `ai/node_types.json`；`python -P ai/info_offsets.py` 后用 `--diff` 比较新旧两份 `ai/out/info_offsets_<版本>.json`，看读属性节点用到的结构偏移有没有变。
7. **实机测试**：用「[W]三国志14优化启动器」启动，看跳过报告、回看报告、府加成、看海接管。没问题后在清单 `versions` 里把新版本标上 `"tested": true`（启动器日志里的「tested / NOT tested」和发布包的检查都读这一项）。
8. **重建发布包**：`python -P release/make_release.py`。它会重新生成 `sigs_gen.h`、重编 DLL，把 `sigs/sigs.json`、`tools/sigs.py`、`tools/sigcheck.py` 放进 `app/`，并检查清单在每个已测试版本的镜像上都能全部命中。

**镜像归档约定**：每个支持过的版本都保留一份镜像，放在 `analysis/`（`analysis/dump_*/` 已在 `.gitignore` 里，不进仓库），一个约 44 MB。目录名是 `dump_<exe 修改时间>_<文件版本号>`，修改时间在前，所以按名字排序时最新的版本排在最后（`disx.py`、`make_node_types.py` 等取最新一份的工具照常用）；`meta.json` 里有 `file_version` 和 `pe_timestamp`。清单 `versions` 的 `dump` 指向该版本的镜像，`sigcheck.py --version`、`sigfind.py --old/--new` 按版本号找镜像。1.0.2.58226 的镜像是旧命名 `analysis/dump_1793841123/`（`meta.json` 已补上版本号）。sigfind 需要旧版本的镜像才能找回，所以旧镜像不要删。

**自检和演示**：`python -P tools/sigfind.py --selftest` 在 1.0.2.58226 的镜像上做三项（2026-11-12）：
- A. 每条特征码故意改坏两个字节：19 条全部找回原位置，字段值完全一致。
- B. 只用锚点、不和旧函数比相似度：14 条全文扫描的特征码里 9 条锚点就能唯一确定；`report_callback`、`area_bonus`、`auto_check`、`player_force_getter`、`data_root`、`bt_condition_cb` 是只引用数据根的小函数或只有一个常数锚点，要靠相似度，在 A、C 里都找对了。
- C. 模拟更新（特征码里一个结构偏移或常数加 8）：16 条全部找回原位置；其中 5 条改到的是代码依赖的值（子阶段偏移、玩家势力偏移、城市数组偏移），正确地标成「需要人工确认」。

另外做过一次完整演示：用镜像造了一个假的 1.0.2.60000（改了 `report_enter`、`area_bonus`、`data_root` 各一处），sigcheck 报跳过报告、府加成、AI 记录不可用；sigfind 找回前两条、把 `data_root` 标成需要人工确认（城市数组偏移变了）；写回清单副本后，新版本上除 AI 记录外全部可用，1.0.2.58226 仍然全部可用。DLL 的多变体也验证过：给 DLL 的 7 条特征码各加一个坏的第一变体，DLL 全部退到第二变体，地址一致。

**评估：按功能分别停用**。已做最小改动（`report_button.run_partial`）：第 5 版补丁对不上时，用 `sigcheck.check_features` 按功能检查，府加成和看海接管单独运行，提示里列出停用的功能。没拆开的是跳过报告的第 5 版、第 6 版和回看按钮：它们共用状态栈读取（`gamestate.Game`）和按钮程序的主循环，第 5 版对不上而第 6 版（DLL）还能用的情况，要把 `Helper` 改成不依赖第 5 版才能利用，改动较大，没有做。

**评估：`ai/info_names.json` 的结构偏移能不能自动重新提取**：能。原型是 `ai/info_offsets.py`：经节点工厂找到每种读属性节点的虚表，第 16 项是执行函数，按 switch 的每个分支列出读的字段（直接读的，或调用只读一个字段的小取值函数的）。在 1.0.2.58226 上，`info_names.json` 依据里写了字段偏移的 42 条有 39 条对得上（另 3 条是编号 0 走公共分支、耐久是计算出来的）。新版本时对新旧两份结果做 `--diff`，会列出哪个编号读的字段变了；用改过人物「身份」偏移（+0x11e → +0x126）的假镜像验证过，能准确报出来。没做的：自动改写 `info_names.json` 的说明文字，以及把变化自动对应到 `gamedata.py` / `observe.py` 里的偏移，目前要人看 `--diff` 结果手改。

## 第 6 版：在报告流程开始前跳过（0.4.0，DLL 里实现）

v5 让报告流程照常走，只把报告窗口变空，所以前面的「隐藏地图界面 + `CReportWaitState` 等满 2 秒」还在，每回合开头会停顿约 2 秒。v6 参考了社区工具「三国志14 优化伴侣」的做法：在报告流程开始之前就拦下。

- `bin/san14_overlay.dll` 收到 `skip_req = 1` 后，另开线程按 RTTI 名找到 `CUserStrategyState` 和 `CReportWaitState` 的虚表，再用特征码核对并取出需要的函数（全部对不上就 `skip_state = 3`，什么都不挂）。然后替换两个虚表的第 5 项（Update）。
- `CUserStrategyState::Update` 的替身：状态在栈顶、子阶段为 0、不是看海时，执行报告回调 `4569e0` 的函数体（不唤醒协程）：显示 HUD、恢复进行按钮、子阶段设为 1；再调用虚表第 3 项（恢复：HUD、地图输入回调）和第 11 项（参数 0，打开命令界面，子阶段变 2），最后播放协程收尾时的回合开始提示音。然后调用原函数，它读到子阶段 2，同一帧就进入下命令。
- 回看报告：Python 把共享内存里的 `reopen_req` 加 1；替身在子阶段为 1 或 2 时把子阶段改回 0，原函数照常跑游戏自己的报告流程；`CReportWaitState::Update` 的替身让这一次等待在第一帧就结束。`reopen_ack` 回报已执行；Python 等 2 秒没回应就把请求撤回（`reopen_req = reopen_ack`）。
- Python 端先照旧打 v5（它也是版本检查），DLL 的跳过生效后再撤掉 v5；撤不掉就把 `skip_req` 改回 0，只用 v5。两者不能同时开：v5 会把回看的报告也变空。
- 离线测试：`python -P overlay/build.py --test` 把最新的内存转储映射到原基址，跑一遍定位逻辑，打印找到的每个地址。
- 定位用到的函数（RVA 对应下面的版本）：栈顶判断 `573b30`、看海判断 `336c60`、状态管理器 `11060`、按名找状态 `573950`（`"CGameState"`）、恢复进行按钮 `457c20`、第 3 项 `44bfa0`、第 11 项 `44e140`、提示音 `572af0` / `572b20` / `5184b0`。

## 按钮是怎么弹出原版报告的（v5 模式，DLL 不可用时）

1. 撤掉 v5 补丁（恢复报告窗口的 Enter）。
2. 把 `CReportWaitState::Update` 里 `cmp eax, 2000` 的常数临时改成 0，让等待在下一帧就结束（不往游戏对象里写数据，避免写进已释放的内存）。看到 `CReportDisplayState` 后立刻改回 2000；`apply()` 也会兜底改回去。
3. 把 `CUserStrategyState` 的子阶段改回 0，游戏会自己重跑报告流程。
4. 等报告关闭、子阶段回到 1 或 2 后，重新打上 v5 补丁。

`CReportWaitState` 本身只是计时器：Enter 什么都不做，Update 在某个全局标记等于 1 或超过 2000 毫秒时弹出自己，Exit 只负责调用回调、唤醒报告流程。按钮只在 `CUserStrategyState` 位于栈顶、子阶段为 1 或 2（地图上下命令）且游戏在前台时显示。

## 游戏里的结构（RVA 对应上面的版本）

- 状态机：类都继承 `IGameState`，类名靠 MSVC RTTI 读出。状态栈管理器是一个函数内静态对象，RVA `0x1B67310`：`+0x10` 是数量，`+0x20` 是数组指针，`+0x30/+0x38/+0x40` 是切换请求队列。状态只有在栈顶时才会执行 Update（`573b30`）。
- 战略阶段时的状态栈：`CRootState > CMotorGameState > CGameState > CStrategyState > CUserStrategyState`。
- `CUserStrategyState::Update`（虚表第 5 项，`4506e0`）按子阶段 `+0x470` 分支：0 是报告流程，1 是下命令，5→6→3，3 是 `43dbb0`，4 是弹出自身。
- 报告流程 `459d30` 是协程，运行在状态工作线程上：
  1. 先调用 `336c60()`，判断 `CGameState` 的模式是否为 1，也就是看海；是的话直接返回。
  2. 压入 `CReportWaitState`，它最多 2 秒后自己弹出。
  3. 压入 `CReportDisplayState`，等它结束。
  4. 恢复界面标记。
- 等待和唤醒：`575c10` 让出执行并在 WaitForSingleObject 上等待，`5743e0` 负责唤醒。
- `CReportDisplayState` 的虚表在 `1433ca8`：Enter 是 `67fca0`，Exit 是 `67fa90`，Update 是 `67fe80`。子状态 `+0x470` 的含义：0 是行动报告页，1 是收支报告页，2 是开始关闭，3 是动画结束后弹出自身；`+0x474` 是界面动画状态，3 表示可以交互。
- 报告结束回调是 std::function 的 lambda，`_Do_call` 是 `45aab0`，最终调用 `4569e0`：唤醒协程、刷新地图界面，并把 `CUserStrategyState` 的子阶段设为 1。
- 页面切换函数是 `6812e0(窗口, 页号)`；`6851c0` 是窗口的事件处理，负责从第 0 页切到第 1 页，以及开始关闭。

## 补丁的几个版本

- **v1（不要用）：** 在 `459df7` 用 jmp 跳过压入 `CReportDisplayState` 那一步。结果子阶段一直停在 0，报告流程每 2 秒重跑一遍，游戏卡住。
- **v2（不要用）：** 在 v1 的基础上执行回调函数体（跳过唤醒那一步），子阶段能变成 1，但战略界面不恢复，还是卡住。
- **v3（已弃用）：** 改 `CReportDisplayState::Update` 里「子状态 0」的 je（`67febf`），让它跳到「子状态 2」的关闭处理，只改 1 个字节。能正常过回合，但窗口会走一遍打开和关闭动画，一闪而过。
- **v4（已弃用）：** 改 `CReportDisplayState::Enter`（`67fca0`），把 `67fd47` 处「子状态 = 4，打开第 0 页」的 20 个字节换成「子状态 = 3，动画状态 = 3」。页面不建了，但窗口背景还会闪一下。
- **v6（0.4.0 起，DLL 可用时）：** 见上面「第 6 版」，在报告流程开始前跳过，没有 2 秒停顿。
- **v5（DLL 不可用时的后备）：** 在 v4 的基础上，把 Enter 开头分配根界面的 `mov ecx,188h`（`67fcb2`）换成 jmp，跳到 `67fd2c`，连根界面也不创建。Exit 会先检查根界面是否为空，析构函数不碰根界面。第一帧 Update 就走「动画结束 → 弹出」：Exit 重新显示 HUD，回调把子阶段设为 1。用户确认不闪了。

教训：跳过某个界面时，让它的状态照常压入和弹出（保留 Enter、Exit 和回调），只拿掉中间的显示部分，比整个跳过再自己补回调可靠。

## 走过的弯路

- Frida Stalker 会让游戏崩溃（访问冲突，出错位置在 Stalker 生成的代码里），不要用。
- 调用栈采样（`tools/stack.py`，外部挂起线程后用 StackWalk64 回溯）是安全的，但找不到界面状态，因为界面是每帧更新的，不会停在某个函数里。
- 有效的方法：在台词表的目录项上设硬件读监视点（`tools/watch_text.py watchaddr`，Frida 设置 DR0–DR3，不改代码）。抓到读取台词的调用栈后，顺着调用者和 RTTI 往上找到状态类。
- 台词文件 `msggame_exce.bin` 的格式：zp1 解压后，头部有 10 个（偏移, 大小）段；每段开头是条目数，接着是 u32 偏移表（相对段首）。收支报告军师台词在第 2 段第 467–472 条。
